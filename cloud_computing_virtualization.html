Foundation

Cloud Architecture

The components, databases, software capabilities, and applications used to leverage cloud resources for business solutions.

The Goal of Architecture

The entire cloud architecture is aimed at providing users with:

  • High bandwidth & uninterrupted access
  • On-demand agile network mobility
  • Robust network security

Step-by-Step Design Process

Core Principles of Design

All technical solutions should follow these six target principles to ensure a robust architecture.

Architecture Design

Principle 1: Reasonable Deployment

01

Public Cloud

Deployment of business systems available to "any" user.

  • • Cloud hosts (Virtual Machines)
  • • High-performance physical hosts
  • • Hosted applications & servers
02

Private Cloud

Operating system extracted and packaged as software deployed in a user's private environment.

  • • Available only to select users
  • • High security and control
03

Hybrid Architecture

Enables unified management and scheduling of resources across diverse environments.

  • • Public + Privatized platforms
  • • VMware, OpenStack
  • • Physical servers integration
Architecture Design

Principle 2: Business Continuity

Ensuring services remain available despite failures or disasters based on three core aspects.

High Availability (HA)

Avoiding business interruption by using redundancy and other failover designs when the primary resources running the business fail.

Continuous Operations

Ensuring that the resources required for business operations are fault-free, allowing the business to continuously provide uninterrupted services.

Disaster Recovery (DR)

The ability to completely restore applications and data in different, secondary environments when the primary business operating environment is damaged or destroyed.

Architecture Design

Principle 3: Elastic Expansion

Tightly coupled systems are hard to expand and troubleshoot. The first step is to decouple system components.

The Problem

Tightly Coupled Systems

When components are deeply intertwined, scaling one piece forces scaling the whole. Software bugs and system failures become highly difficult to isolate and troubleshoot.

The Solution

Component Decoupling

  • ✓ Statelessness: Remain stateless at the app tier and store state/dynamic data externally (e.g., in Redis).
  • ✓ Load Balancing: Insert load balancers so horizontal scaling doesn't affect the overall business logic.
  • ✓ Message Queues & API Gateways: Producers and consumers can be expanded completely independently without affecting each other.
  • ✓ Global LB: Achieve global load balancing to expand back-end business in hybrid/multi-cloud environments.
Architecture Design

Principle 4: Performance Efficiency

1. Computing

Improve single-machine performance using high-configuration cloud hosts. Expand overall service performance through horizontal clustering.

2. Storage & Caching

Cache hot data and store temporary state data using Redis. Perform in-memory calculations to drastically reduce I/O wait and improve speed.

3. Network Opt.

Select optimal data centers for global deployments. Route traffic intelligently using global infrastructure networks and CDNs.

Architecture Design

Principle 5: Security Compliance

Meeting internal security protection needs while adhering to external supervision and regulatory requirements.

Identity & Access Management

Set up master and sub-accounts. Manage public/private keys separately. Assign minimum required permissions (Principle of Least Privilege) to specific roles.

Network Isolation

Control access via ACLs and Security Groups (port restrictions). Control cross-subnet communication through strict routing rules and VPC boundaries.

Data & Intranet Protection

Databases and internal cloud hosts must reside in isolated Intranet VPCs. Do not connect them to the extranet (public internet) directly.

Threat Mitigation & Auditing

Implement WAFs to prevent DDoS, SQL injection, XSS. Maintain continuous security auditing, keep access/operation logs, and archive them securely.

Architecture Design

Principle 6: Continuous Operation

1. Monitoring & Alarming

Continuously monitor cloud resources, services, events, and user applications. Establish strict alarm thresholds.

2. Multi-Channel Notification

When alarms trigger, automatically notify personnel via phone, SMS, email, WeChat, or Slack channels immediately.

3. Automated Response (Callbacks)

Route alarms to callback functions (e.g., AWS Lambda) to execute contingency plans and realize automated fault handling without manual intervention.

4. Auto-Scaling & Cost Control

Automatically expand or shrink cloud hosts based on CPU/Memory metrics. Detect consumption changes to optimize costs. Set account balance alarms to prevent budget overruns.

Cloud Environments

Benefits

  • • Accessibility anywhere, with any device
  • • Ability to get rid of most or all hardware and software management
  • • Centralized data security and backups
  • • Higher performance and multi-region availability
  • • Quick application deployment (CI/CD)
  • • Instant business insights via managed analytics
  • • Business continuity and automated disaster recovery
  • • Price-performance and capital cost savings (Pay-as-you-go)
  • • Cloud computing is generally "greener" (efficient shared data centers)

Limitations & Issues

  • Sensitive Data Control Handing over extremely sensitive IP or PII data to a third-party vendor involves loss of absolute physical control.
  • Application Development Lock-in Building heavily on provider-specific APIs (like AWS Lambda or DynamoDB) makes migrating to another cloud difficult.
  • Third-Party Security Level You are reliant on the provider's security posture. If they have a hypervisor breach, your VMs could be exposed.
  • Issues of Regularity Government policies and data sovereignty laws (e.g., GDPR) dictate where data can physically reside, complicating global cloud deployments.

High-Performance Computing (HPC)

HPC is the ability to process data and perform complex calculations at incredibly high speeds.

Standard Desktop (3 GHz) ~3 Billion / sec

HPC Supercomputer Quadrillions / sec

The best-known HPC solution is the supercomputer. It contains thousands of compute nodes working together to complete tasks via parallel processing.

3 Main HPC Components

1. Compute Cluster Hundreds or thousands of networked compute servers (nodes) running software simultaneously.
2. High-Speed Network Must transport massive amounts of data instantly between nodes and storage without bottlenecking.
3. Data Storage Must feed and ingest data to/from compute servers precisely as fast as it is processed.

Service Models

Utility Computing

The Pay-Per-Use Paradigm

Utility computing is the most trending IT service model. It provides on-demand computing resources (computation, storage, and APIs) and infrastructure based entirely on a pay-per-use method, much like water or electricity.

Key Advantages:
  • • Minimizes upfront associated costs (CapEx).
  • • Maximizes efficient use of resources.
  • • Provides greater flexibility and easier management.
  • • Championed by large orgs like Google and Amazon (AWS).

Utility Computing Offerings

  • ▹ Access to file, application, and web servers.
  • ▹ Full stack: IaaS, PaaS, SaaS.
  • ▹ Virtually unlimited processing power and storage.
  • ▹ Cloud storage and general cloud computing.
  • ▹ Utility services: Power, HVAC, and communications in datacenters.
  • ▹ Specialized expertise (ransomware response, dev support).
Distributed Power

Grid Computing

Combining computing resources from multiple, geographically distinct locations to achieve a common goal.

1. Control Node

A group of servers running specialized software that administers the entire network, acts as the manager, coordinates tasks, and assigns subtasks.

2. Provider

A computer (or server) that contributes its spare processing resources into the network resource pool.

3. User

The computer/application that actually requests and uses the aggregated resources on the network.

How it Works

The grid is connected by parallel nodes forming a computer cluster (of varying sizes and OSs). The manager software breaks a massive job into subtasks and distributes them.

Main Application → Manager → Data Grid Nodes

Nodes work simultaneously. Outputs are gathered and aggregated to complete the larger-scale task. Used in ATMs, back-end infrastructures, and research.

The Core Engine

What is Virtualization?

"The creation of a virtual (rather than actual) version of something, such as a server, a desktop, a storage device, an operating system, or network resources."

It allows sharing a single physical instance of a resource among multiple customers and organizations. It logically separates the environment from the underlying hardware by assigning a logical name and a pointer to the physical resource.

Virtual Machine (VM)

An isolated environment logically separated from underlying hardware. Operates like a typical physical server with its own CPU, RAM, OS, and apps.

Host vs. Guest

The physical machine running the virtualization software is the Host. The virtual machine running inside it is the Guest.

Virtualization vs. Cloud

Virtualization is the technology that splits hardware. Cloud Computing is the business model that delivers those virtualized resources over the internet on-demand.

Why Use Virtual Machines?

🖥️

Run operating systems where the physical hardware is unavailable.

⚡

Easier to create new machines, backup, and restore rapidly.

🧪

Safe software testing using "clean" snapshot installs of OSs.

🪄

Emulate more machines than are physically present.

⏱️

Timeshare lightly loaded systems efficiently on one host.

🐛

Debug easily (suspend/resume state of the problem machine).

🚚

Live migration of VMs between physical servers without shutdown.

💾

Run legacy systems safely inside a modern infrastructure.

VMM installed on hardware (Servers). Full, Emulation, or Para-virtualization.

2. Operating System

Deep Dive

Hardware Virtualization

Mainly done for server platforms. Divided into three sub-types.

1. Full Virtualization

Underlying hardware is completely simulated. Guest OS requires zero modifications. Relies heavily on Binary Translation and hardware assists (Intel VT-x, AMD-V) to trap privileged instructions.

Complete Isolation

2. Para-Virtualization

Hardware is not fully simulated. The Guest OS is modified to replace non-virtualizable OS instructions with hypercalls to the hypervisor at compile time. Higher performance.

Modified Guest OS

3. Emulation

The virtual machine software simulates the entire hardware architecture in software, making it completely independent of the host CPU. Slowest, but allows running entirely different architectures.

Hardware Independence

Full Virtualization & Rings

x86 Privilege Rings

Standard x86 architecture has Rings 0, 1, 2, 3. The lowest number has highest privilege (hardware access).

  • Ring 0 Hypervisor / VMM
  • Ring 1 Guest OS (Unmodified)
  • Ring 2 (Rarely used)
  • Ring 3 User Applications

Binary Translation

Because the Guest OS is at Ring 1, it cannot execute privileged hardware instructions directly. The VMM scans the instruction stream. When a critical instruction is found, it is trapped and Binary Translated on the fly into safe code that emulates the behavior.

Advantage

Best isolation and security. Unmodified OS can run. No hardware assist strictly required.

Disadvantage

Binary translation is time-consuming. Memory overhead for code cache. 80-95% native performance.

Para-Virtualization

Compiler Support & Hypercalls

Instead of translating instructions on the fly at runtime, Para-virtualization handles them at compile time.

The Guest OS kernel is intentionally modified by an intelligent compiler. Non-virtualizable, privileged instructions are explicitly replaced with Hypercalls (APIs) to communicate directly with the hypervisor.

Guest OS → executes Hypercall → handled by VMM Service Routine
Performance Win

Because there is no costly binary translation trap-and-emulate overhead, para-virtualization generally offers near-native performance.

The Trade-off
  • • Requires access to modify the Guest OS source code (easy for Linux, hard for Windows).
  • • High maintenance cost for patched OS versions.
  • • Compatibility issues with unmodified systems.

Host-Based Virtualization

A virtualization layer is installed on top of a complete Host OS (e.g., Windows running VirtualBox). The Host OS remains responsible for managing hardware drivers.

Pros

  • • Easy to deploy without modifying the host OS.
  • • Relies on the host OS for hardware device drivers (very flexible).
  • • Great for desktop testing.

Cons

  • • 4 Layers of Mapping: App → Guest OS → Virtualization Layer → Host OS → Hardware.
  • • Significant performance downgrade due to overhead.
  • • Too slow for heavy, practical enterprise server deployments.
Architecture

Xen Hypervisor

An open-source micro-kernel hypervisor that uses Domain hierarchy.

Dom0 (Domain 0)

Privileged Domain / Host

The first domain started by Xen. It has special privileges to access hardware directly and start new domains. Runs device drivers and the BackendDriver which multiplexes hardware requests from other domains.

Usually runs a heavily patched Linux kernel.

DomU (Domain U)

Unprivileged Domain / Guest VM

The standard virtual machines. They have NO direct hardware access. They run a FrontendDriver that passes requests to Dom0 via the hypervisor to access networks and disks.

Started by XenD in Dom0 using the 'xm' tool.

The Hypervisor: Sits below Dom0 and DomU, checking page tables, allocating resources, scheduling domains, and booting the machine to start Dom0.
Architecture

KVM (Kernel-Based VM)

Linux Integration

KVM is a full native virtualization solution built directly into the standard Linux kernel (since 2.6.20). It interfaces via a loadable kernel module.

It utilizes hardware virtualization extensions (Intel VT, AMD-V) for full virtualization, but also supports para-virtualized network drivers for performance.

VMs as Processes

In KVM, a virtual machine is implemented simply as a regular Linux process. Each virtual CPU is just a standard thread.

Advantage: Memory management and scheduling are handled entirely by the robust, standard Linux scheduler. This makes KVM simpler than standalone hypervisors.

5 Implementation Levels of Virtualization

Where is the virtualization layer inserted in the stack?

5. Application Level Highest Level
4. Library Level User APIs
3. Operating System Level Kernel / Containers
2. Hardware Abstraction Level (HAL) Hypervisor
1. Instruction Set Arch Level (ISA) Deepest / Emulation

Deep Virtualization

1. Instruction Set Architecture (ISA) Level

Works via ISA emulation. Translates binary code written for one hardware configuration so it can run on another (e.g., legacy code on an x86/x64 machine).

Uses a basic interpreter to read source code and convert it to hardware-readable format. Makes the VM hardware agnostic.

2. Hardware Abstraction Level (HAL)

Virtualization performs right above the hardware level using a Hypervisor. Manages CPU, Memory, and I/O devices.

Allows multiple isolated VMs to run simultaneously on the same hardware. Standard for cloud-based infrastructure (e.g., VMware, Xen).

Higher Virtualization

3. OS Level

Creates an abstract layer between the OS and application. Shares the host OS kernel to create isolated containers (e.g., Docker). Ideal when users don't need a custom OS, preventing resource conflict efficiently.

4. Library Level

Because full OS virtualization can be cumbersome, this level intercepts user-level API calls from libraries. Uses API hooking to control communication from the app to the system (e.g., WINE on Linux).

5. Application Level

Virtualizes only a single application environment rather than the whole platform. Typically implemented using a Virtual Machine executing high-level byte-code (e.g., JVM for Java, .NET CLR).

Hands-on Service

Amazon EC2

Elastic Compute Cloud: The virtual server in the cloud.

The EC2 Instance

An EC2 instance is simply a virtual machine running in AWS's data centers. You rent computing power by the hour/second.

  • • Choose your OS (Linux, Windows, macOS).
  • • Choose CPU, RAM, and Storage sizing.
  • • Scale horizontally automatically.

The Nitro System

AWS moved away from traditional heavy hypervisors to their custom Nitro System.

It offloads hypervisor functions (network, storage, security) to dedicated hardware cards. This leaves practically 100% of the physical server's CPU and RAM available for the guest instances, blurring the line between bare-metal performance and virtualization.
